# Agent Note: Messages queued together are delivered as one RLM continuation

Status: implemented

English | [中文](2026-10-16-rlm-message-batching.zh.md)

## Problem

Each message queued for an RLM session used to start its own continuation, one after another. In the frozen evaluation run `run-e5976e34` (source `b980e8b69c`, arm C), every one of the six nodes had a root that spawned two children; each child sent one result message; the root was continued once per message, so twelve continuations. In all six nodes both messages were in the runtime's record before the first `rlm.message.delivered` event, and the final text of the second continuation was byte for byte the text of the first. Whether the second message was already queued when the first was chosen is not recorded. The second continuations account for about 108 s between their `delivered` and `continuation.settled` events and for 68843 uncached input, 19625 output, and 152960 cache-read tokens in the usage records attached to them. Those are quantities that belong to those commands, not savings: a merged execution can cost more or less, the interval is not request time, and identical final text does not show that the second execution added nothing. The physical request count and the provider's bill for these runs are unknown.

## Decision

**Messages queued together for one session share one continuation.** `pumpSessionMessage` takes the first message in delivery order and the messages directly after it for as long as each one is an agent message with the first message's delivery mode and the rendered instruction stays within 16384 UTF-16 code units. It stops at the first message that does not qualify and never skips it. A controller's input (the recorded `source: control`, or a `controlLeaseId`) is always alone, because it may change the task; nothing reads message text. A first message that is longer than the threshold is delivered alone and whole as before, so the threshold decides who shares a continuation and is not a limit on the prompt. The member list is fixed before the host is called; messages that arrive later wait for the next batch.

**One batch is one worker command.** A single message keeps `<messageId>:deliver`; a larger batch is `<first messageId>:batch-<size>-<digest of the ordered ids>:deliver`, so a retry with another member set never reuses the command of an earlier attempt, and anything that matches commands by their `:deliver` suffix still works. `dispatchContinuation` receives the ordered `messageIds` (`RlmMessageV1['messageId']`); the field is optional only for goal, heartbeat, autonomous and older callers, and the daemon refuses a message continuation without it before any execution exists. Each member keeps its own `rlm.message.delivered` and terminal `rlm.message.continuation.<status>` events with the shared `commandId`, `batchIndex`, `batchSize`, result reference, `stopReason` and status exactly as the execution reported them. Usage is the usage of the command: one logical execution may run several tool rounds and requests, so it is summed per command and never per message or by result reference (two different executions can produce the same artifact and each is counted).

**The batch is recorded before the host is called.** The state file gains `messageBatchDispatches` (`{commandId, sessionId, messageIds, state, createdAt}` with `intended`, `accepted`, `held`) and its version becomes 6. The record is written before `dispatchContinuation`. A host error with code `RLM_DISPATCH_NOT_ADMITTED`, thrown by the daemon for failures that precede any native execution, is the only thing that removes the record and keeps the members queued. Everything else that can follow a possible admission holds the batch: any other error, a restart that finds `intended`, a write that fails after the host answered (the file may still say `intended` or already say `accepted`; the next start reads it and does not guess), a session deleted while the host answered, and an accepted execution that could not be registered and could not be interrupted. A held batch is never selected again and the session receives nothing more; `drain` does not report it idle; a `rlm.message.dispatch_unknown` event names the command and members. The members are delivered and the record becomes `accepted` in one write, and the record leaves with the terminal events. An accepted execution that cannot be registered because the session already has one is interrupted and stays counted by `drain` until its own result settles, because an interrupt that returns is not a stop; its members stay delivered. This differs from before, when a failure after the host answered could return a delivered message to the queue and send it again.

**The terminal state is the execution's.** `settled`, `failed`, and `indeterminate` and the `stopReason` are written to every member as reported; `indeterminate` is never turned into `failed`. A delivered message with no terminal event means no outcome was observed (a restart loses the execution); that is told apart from an explicit `indeterminate`, and neither is sent again.

**State version 6 is read and nothing older.** Construction reads version 6 only and refuses every other version, a version 6 file without the array, and a batch record that disagrees with the messages (duplicate or unknown members, another session, a command that does not match its members, members out of delivery order, a state that disagrees with the delivery of its members), before registering the runtime owner, and it writes nothing: the refused file keeps its bytes. The migration of versions 1 to 4 and the version 5 shape were removed with their tests, because a migrated version 5 file would have to claim that no dispatch is in flight, and a runtime that stopped mid-dispatch leaves exactly the window this record exists to close. A Provider that reads up to version 5 refuses a version 6 file by its version check; no experiment on an older build was run.

## Alternatives considered

**Skip the second continuation when its outcome looks covered.** Rejected: it needs a judgement about meaning, and identical output on six tasks is not evidence for other tasks.

**Take every queued compatible message.** Rejected: delivery order is part of the contract, and skipping an incompatible message in the middle would deliver messages out of order or past a controller's input.

**Migrate version 5 by adding an empty array.** Rejected as above.

**Deduplicate usage by result reference.** Rejected: distinct executions can produce the same artifact.

**Persist a frozen member set instead of deriving the command from it.** The persisted record is what carries the members. The derived command keeps a changed member set from reusing an earlier command and keeps single-message commands unchanged.

**A new host error taxonomy.** Not done: one code names the one fact the runtime needs, that no execution exists.

## Consequences

For tasks like those measured, the number of continuations can fall to one per batch, which is a structural change that depends on the arrival of the messages. What it does to time and tokens is not established: the request count and bill of the baseline are unknown, and a single comparison cannot show significance. A message the model would have seen alone is now seen together with others, in order. A session with a held batch stops receiving messages until its state file is dealt with by hand; nothing reconciles it. Because the state version changed, this build cannot open state written by earlier builds. A Desktop release that contains this change needs its own reviewed migration decision for the version 5 state of installed users; an evaluation uses a new, empty home. The sealed `rlm-runtime`, `rlm-runtime-local` and `orchestration-local` packages change.

The tracking of an accepted execution lasts for the life of the process. After a restart a batch that was accepted and has no terminal event stays as it was (its members are delivered, none is sent again), `recoverUncertainWork` turns only `intended` into `held`, and the execution handle is gone, so `drain` reporting idle after a restart does not show that the remote execution has stopped. Nothing here reconciles that, and this note does not extend to cancellation, goals, or heartbeats.

## Testing

`message-batch.spec.ts` covers batching and the single-message bytes, controller isolation and the rule that a controller's input is not skipped, steer-before-follow-up order and ties, a message that arrives while a batch is handed over, a refusal before admission and the retry under another member set, a held batch (the session receives nothing more, also after a restart), a batch found `intended`, a failed write after the host answered, an accepted execution that cannot be registered (counted until its result settles, held when it cannot be interrupted), a session deleted while the host answers, terminal states and stop reasons for all three statuses, a rejected result, the same result artifact from two executions, the batch on disk when the host is called, and the threshold at exactly 16384 and 16385 code units, surrogate pairs and artifact references. `runtime.spec.ts` covers refusing versions 1 to 5 and 7 by name, a version 6 file without the array, and each kind of inconsistent batch record, each with the file's bytes unchanged. `rlm-continuation.spec.ts` covers the refusal marking and the plural wording. The `prime-rlm-terminal` snapshot adds a `batched-messages` scenario through the production Loader and daemons with only the model provider replaced: two children report before the root's turn ends, the batch continuation runs three tool rounds with different usage and cache hits (it spawns a third child in the first round), and a second, single-message continuation follows with two rounds. The transcript holds the batch command and its members' events, both continuation artifacts as the artifact service returns them (command, ordered messages, answer, stop reason), that the node's output is the last continuation's answer and not the root's own, the usage the fake served in each round with its sums, and the one `rlm.usage` record of each command, which equals those sums. The two artifacts differ because the command is part of their content. `prime-rlm-e2e.spec.ts` now compares the continuation events with the runtime's own record of the two messages. Twenty-four controls that each break one rule were run with the file's bytes restored afterwards, and their logs are in the evaluation report directory: the first round had six that did not fail by assertion and were kept as a record, the second round repeated all twenty, and the last four cover the same-result terminal events, per-round cache summing, the artifact's members, and the command under which usage is recorded. The same-result test shows that two executions with one result artifact each get their terminal events; it carries no usage.

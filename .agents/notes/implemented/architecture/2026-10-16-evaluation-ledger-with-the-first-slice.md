# Agent Note: The evaluation ledger meets the child context, result reading and batched continuations

Status: implemented

English | [中文](2026-10-16-evaluation-ledger-with-the-first-slice.zh.md)

## Problem

Two changes were made on separate bases. The evaluation request ledger ([note](2026-10-15-evaluation-request-ledger.md)) admits and accounts for every physical model request of an API worker under an evaluation scope. The first slice ([note](2026-10-16-rlm-child-context-and-result-retrieval.md)) gives a child its own context, lets a parent read a stored child result, and delivers queued messages as one batched continuation. Merged, three questions were open, and each has an observed answer.

1. **A command's usage.** The DeepSeek worker adds the usage of the rounds that report one and skips a round that reports none. A command whose second request carried no usage was published as a command with the usage of its first request, as if that were its cost.
2. **A failure with a request outstanding.** The ledger holds a request that ended without usage as `unknown`, because it may have been processed and billed. A worker reports a failed request either by throwing (for example `MODEL_WORKER_INVALID` after a round that returned no tool call) or as a result that stopped with an error. Nothing tied either to the ledger, so a node whose retry policy lists the thrown code could replay a command whose earlier request had an unknown outcome.
3. **Where requests leave the daemon.** Whether the batched continuation, a child result read, and a round after it are all admitted, one request at a time, before they are sent.

## Decision

**One place, under a scope only.** `executeModelWorker` in `daemon.ts` is the one function through which the child, continuation, root and plain-node dispatches reach the worker. Outside a scope it calls the worker as before. Under a scope it counts the admissions the worker makes for the command, and when the command ends it reads the command's rows back from the ledger (`attemptsOf`, which counts rows one by one and relates a row to a command through the label `<command>#plain` or `<command>#round<N>@<session>`; a label never decides how many requests exist).

**The account is separate from the outcome.** An `evaluation.command.metering` event records, apart from how the command ended (returned with a stop reason, or failed with a code): whether the account is complete, the admission calls, the rows, how many were sent and refused, the usage the ledger holds for the settled ones, the requests that lack usage, and every row with its id, sequence, round, session, state and body hash. The account is complete when every admission call has a row, no row is reserved or unknown, and the worker asked to admit at least one request (`accountOf`); a command whose only request was refused is complete, with nothing sent. The event is the ledger's account at the moment the command ends; a later `reconcile` of a late receipt changes the ledger, not the event.

**An incomplete account withholds the usage.** When it is incomplete, the usage of the worker's result is removed, so no consumer (`rlm.usage`, goal and autonomous accounting, node evidence) reads a sum of the known rounds as the cost of the command. The known part is in the event. Missing usage is not filled with zero. `rlm.autonomous.usage` writes `0` for a command without usage; that is not a bill.

**A failure with an outstanding request is an unknown outcome.** When a command that its caller did not cancel throws, or returns a result that stopped with `error` or `aborted`, while the ledger holds a request of it as reserved or unknown, it is rethrown as `COMMAND_INDETERMINATE` through `UnknownPhysicalOutcomeError`. The node is then `indeterminate`, a child's lifecycle is `indeterminate`, and the members of a continuation end `indeterminate`. The identity has to survive the consumers that read a continuation's status, so it is also given where the ledger is the evidence: a goal continuation or an Autonomous direct continuation that ended `indeterminate` while the ledger holds a request of its command as reserved or unknown, and an Autonomous root turn that stopped with `error` or `aborted` while a request of the session is reserved or unknown (as after an unknown message continuation), are rethrown the same way. Before this, they became `NODE_INDETERMINATE` and `ORCHESTRATION_UNAVAILABLE`, which a retry policy can list. The same codes from other causes, and every home without a scope, are unchanged. A command, goal continuation, Autonomous direct continuation or Autonomous root turn whose execution its caller cancelled keeps the error it had and the run stays `cancelled`; the request stays `unknown` in the ledger. Two aborts leave the run running and are not a cancellation: the attempt's own deadline (`timeoutMs`), which aborts with `AttemptDeadlineError`, and an interrupt of the root session by the runtime, which aborts with `RootInterruptedError`. The check reads these reasons, not an error message; a cancellation or shutdown of the run, and the interrupt of a child, keep the default reason. A request left unknown by either is therefore an unknown outcome, the node is `indeterminate`, and no later attempt runs it again although the retry policy lists the codes and has attempts left; a deadline after every request settled is an ordinary failure and is retried. The first abort decides: a cancellation after the deadline already fired is counted as the deadline. By code reading, not tested: the run was then saved as `cancelled` first, and the attempt's `COMMAND_INDETERMINATE` can set it to `indeterminate` afterwards, as before the previous repair; this is an open question. A refusal of admission, which sent nothing, stays an ordinary error stop; a known failure whose requests all settled stays an ordinary failure and may be retried, and the retry runs under a new command with its own rows. If the store refuses the `rlm.execution.failed` notification or the metering event while an unknown outcome is being reported, the outcome keeps its identity and carries the refused write in its cause. The unknown stop of an Autonomous root turn is decided before the Autonomous node's state and its `rlm.autonomous.usage` event are written, so a refused write there is also carried in the cause and does not become an ordinary storage error that the retry policy can replay.

**What is not changed.** A refusal is not mapped to `RLM_DISPATCH_NOT_ADMITTED`, to a busy error or to a queue: the first physical request is refused after the logical dispatch was accepted, so the runtime's rule that only a refusal before a native execution keeps messages queued is unchanged. The ledger's `unknown` and the runtime's `held` stay two separate records, and nothing reconciles them. Resident and remote operators, other workers, calls without an admission, and `proven-token-count` are still refused under a scope. `request-bytes-audited` is still an estimate checked afterwards. Outside a scope the model, effort, capacity, queue, cancellation and request fields are unchanged.

## Alternatives considered

**Change the worker to report incomplete usage.** Rejected: the worker and the adapter are WP1's and outside the scope of this change; the ledger already holds what is needed.

**Add the command, round and session as fields of an attempt.** Rejected: it changes the persisted ledger format, whose reader accepts no unknown field; the label carries them, and the event lists them with the row id.

**Treat a refused first request as a dispatch that was never admitted.** Rejected: nothing proves that the logical command was never admitted, and the case is not distinguished from a refusal that follows a settled round.

## Consequences

Under a scope a command's usage can be absent where it used to be partial. `evaluation.command.metering` is a new orchestration event type, written only in homes with a scope; the store keeps event types as text and no reader validates them; a build without this change was not run against such a home. An outcome the ledger cannot prove is now indeterminate where it was failed: a thrown failure and an error stop with an outstanding request. In the run `unknown-continuation` the members of the continuation are `indeterminate`, while the node is `failed` with `OPERATOR_STOPPED`: that comes from the existing rule that a settled result which did not complete fails the node, and was not changed. A refusal is visible in the ledger row's reason and in the rows of the metering event (`input-exhausted`, `attempts-exhausted`). The worker turns any finish that is not a stop, a length limit or an abort into `stopReason: 'error'` and drops the failure's code (WP1's own `worker-evaluation.spec.ts` asserts the error stop), so `ADMISSION_REFUSED` appears in no orchestration event; in `refuse-first`, `refuse-later` and `refuse-round`, where the refused request ends the root's last command, the node's blocker is `OPERATOR_STOPPED`. This was not introduced by this change and is not mapped here.

## Tests

Each scenario of the `prime-rlm-evaluation` fixture starts the production Loader and daemons with only the model provider replaced, in its own home and process, and every received request is matched one to one with an admitted row by its body digest, and must already be reserved in the ledger file when it arrives. Eighteen scenarios: the original tree; `integration` (a root, two children and one batched continuation of two messages that reads a child result in its first round: eight requests, one continuation command with two rounds); `refuse-first`, `refuse-later` (the continuation's first request) and `refuse-round` (a later round of one command), each with no request sent past the refusal, no requeue, and no `RLM_DISPATCH_NOT_ADMITTED` or busy error in any event; `cancelled` (a run cancelled with a request in flight: the run is `cancelled`, the node `failed`, the request `unknown`, nothing replayed); `missing-usage`; `unknown-no-replay` (thrown), `unknown-error-finish` (an HTTP 500), `unknown-child` and `unknown-continuation`; `unknown-no-replay` and `unknown-error-finish` run with a retry policy that lists the code and `maxAttempts` 2, with room in attempts, output and concurrency, and are not replayed; `unknown-child` and `unknown-continuation` run without a retry policy, so they show the lifecycle of the child and of the members only; `unknown-goal`, `unknown-autonomous` and `unknown-message-autonomous` (an unknown goal continuation, Autonomous direct continuation, and message continuation under Autonomous Mode) run with `maxAttempts` 2 and a policy listing `NODE_INDETERMINATE`, `ORCHESTRATION_UNAVAILABLE` and the other codes those consumers could end with: no `node.retry_scheduled`, the attempt number does not rise, no second root or child request is sent, and the unknown request stays; `known-retry` and `known-goal-retry` (a second attempt metered apart); `zero-child`; and `ordinary` (the same root without a scope: no ledger, and the model, `max_tokens` and effort the home always sent, which differ from the scope's). `evaluation-ledger.spec.ts` covers the label, the row counts, the count of outstanding requests of a session, and the two decisions as functions. `daemon.spec.ts` runs the real daemon, ledger, consumers and retry policy with a worker that has the API worker's id and reserves a request through the scope's admission without sending HTTP. With the daemon's own attempt timer, `maxAttempts` 2 and a policy that lists the codes, it lets the deadline pass while a root's request, or the request of a goal, Autonomous direct or message continuation, is open (the worker returns an aborted stop or throws), and checks that the node is `indeterminate`, its attempt number is 1, no `node.retry_scheduled` was written, the root was sent once and the request is `unknown`; a deadline after the request settled still retries. For each of the goal continuation, the Autonomous direct continuation and the message continuation under Autonomous Mode it cancels the run while the continuation's request is open, lets the worker throw after the cancel, and checks that the run is `cancelled`, the request is `unknown`, and the root is not sent again; it also makes the store refuse the Autonomous node's state, or its usage event, while a message continuation under Autonomous Mode ends in an unknown stop, and checks that the node is `indeterminate`, is not retried although the policy lists the code, and that the write error is in the cause. It also makes the store refuse the failure notification, or the metering event, while a command with an unknown request fails, and checks that the node is `indeterminate`, is not retried, and that the error the attempt handling received keeps its identity and carries the refused write; it retries a node whose command failed in a known way; and it cancels the work of a run so that the worker throws after the cancel, and checks that the error is kept and the request stays unknown. The scenarios were run from source and from the built libraries.

Controls (one rule broken at a time, bytes restored and hashed): for the root interrupt, Y08 (the interrupt aborts with the default reason) turns exactly the root-interrupt test red, and Y03 turns it red together with the deadline test of the thrown branch; for the deadline, Y01 (the deadline aborts with a plain error) turns all five unknown-at-deadline tests red, Y02 and Y03 (the wrapper's returned and thrown branches), Y04, Y05 and Y06 (the goal, direct and message consumers) each turn exactly their own test red, and Y07 (a caller's cancellation never recognised) turns exactly the four cancellation tests red; for the cancellation identity and the order of the Autonomous writes, X00 (the source before the fix) turns all five new tests red, and X01 to X05 each turn exactly their own tests red (the goal, direct and message consumers' cancellation checks one test each; letting a refused write replace the stop, or not carrying it, the two write tests); twelve on the ledger functions (L01–L11 and P08, the session count), all red, and seventeen on the daemon rules (W01–W10 and P01–P07), sixteen of them red on the field they target (for example, without the reclassification `unknown-no-replay` retries and sends three requests; without the withholding `missing-usage` publishes `rlm.usage` for the root; without the identity kept for the goal, Autonomous direct and message-to-Autonomous consumers the three corresponding scenarios retry). One survived and is not covered by these scenarios (W06): the status the runtime keeps for a tracked root execution is held in memory (returned by `drain`) and appears in no event or record, so the mapping that makes it indeterminate cannot be observed in the fixture's outputs; the node's own state follows the thrown error. Two controls survived on their first run and were retargeted, and both first runs are kept: W10 (the cancellation exception on a thrown error), because a cancelled run ends with an error stop in the fixture, now red through the `daemon.spec.ts` test that cancels the work so that the worker throws after the cancel; and P07 (only a command with an outstanding request is reclassified), because the goal consumer asks the ledger for its own evidence, now red through the daemon-level test of a known failure. P08 went red through the unit test. In the first increment's table, the control on the read of the label's command (L10, the usage of non-settled attempts) went red through a `TypeError` on an undefined value, not through the assertion it targets. A Resident child under a scope is covered by the existing `daemon.spec.ts`, not by a scenario; the rule 'only a command with a ledger request in doubt is reclassified' is checked in the positive direction by the scenarios, and in the negative direction by the daemon-level test of a known failure and by `known-goal-retry` (a continuation that fails with no unknown request keeps `ORCHESTRATION_UNAVAILABLE` and is retried).

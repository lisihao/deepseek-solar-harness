# Agent Note: The evaluation ledger meets the child context, result reading and batched continuations

Status: implemented

English | [中文](2026-10-16-evaluation-ledger-with-the-first-slice.zh.md)

## Problem

Two changes were made on separate bases. The evaluation request ledger ([note](2026-10-15-evaluation-request-ledger.md)) admits and accounts for every physical model request of an API worker under an evaluation scope. The first slice ([note](2026-10-16-rlm-child-context-and-result-retrieval.md)) gives a child its own context, lets a parent read a stored child result, and delivers queued messages as one batched continuation. Merged, three questions were open, and each has an observed answer.

1. **A command's usage.** The DeepSeek worker adds the usage of the rounds that report one and skips a round that reports none. A command whose second request carried no usage was published as a command with the usage of its first request, as if that were its cost.
2. **A failure with a request outstanding.** The ledger holds a request that ended without usage as `unknown`, because it may have been processed and billed. A worker reports a failed request either by throwing (for example `MODEL_WORKER_INVALID` after a round that returned no tool call) or as a result that stopped with an error. Nothing tied either to the ledger, so a node whose retry policy lists the thrown code could replay a command whose earlier request had an unknown outcome.
3. **Where requests leave the daemon.** Whether the batched continuation, a child result read, and a round after it are all admitted, one request at a time, before they are sent.

## Decision

**One place, under a scope only.** `executeModelWorker` in `daemon.ts` is the one function through which the child, continuation, root and plain-node dispatches reach the worker. Outside a scope it calls the worker as before. Under a scope it counts the admissions the worker makes for the command, and when the command ends it reads the command's rows back from the ledger (`attemptsOf`, which counts rows one by one and relates a row to a command through the label `<command>#plain` or `<command>#round<N>@<session>`; a label never decides how many requests exist).

**The account is separate from the outcome.** An `evaluation.command.metering` event records, apart from how the command ended (returned with a stop reason, or failed with a code): whether the account is complete, the admission calls, the rows, how many were sent and refused, the usage the ledger holds for the settled ones, the requests that lack usage, and every row with its id, sequence, round, session, state and body hash. The account is complete when every admission call has a row, no row is reserved or unknown, and at least one request was made (`accountOf`). The event is the ledger's account at the moment the command ends; a later `reconcile` of a late receipt changes the ledger, not the event.

**An incomplete account withholds the usage.** When it is incomplete, the usage of the worker's result is removed, so no consumer (`rlm.usage`, goal and autonomous accounting, node evidence) reads a sum of the known rounds as the cost of the command. The known part is in the event. Missing usage is not filled with zero. `rlm.autonomous.usage` writes `0` for a command without usage; that is not a bill.

**A failure with an outstanding request is an unknown outcome.** When a command that nobody cancelled throws, or returns a result that stopped with `error` or `aborted`, while the ledger holds a request of it as reserved or unknown, it is rethrown as `COMMAND_INDETERMINATE` through `UnknownPhysicalOutcomeError`. The node is then `indeterminate`, a child's lifecycle is `indeterminate`, and the members of a continuation end `indeterminate`; none of them is replayed, whatever `retryableCodes` lists. A command cancelled by its caller keeps the error it had. A refusal of admission, which sent nothing, stays an ordinary error stop; a known failure whose requests all settled stays an ordinary failure and may be retried, and the retry runs under a new command with its own rows.

**What is not changed.** A refusal is not mapped to `RLM_DISPATCH_NOT_ADMITTED`, to a busy error or to a queue: the first physical request is refused after the logical dispatch was accepted, so the runtime's rule that only a refusal before a native execution keeps messages queued is unchanged. The ledger's `unknown` and the runtime's `held` stay two separate records, and nothing reconciles them. Resident and remote operators, other workers, calls without an admission, and `proven-token-count` are still refused under a scope. `request-bytes-audited` is still an estimate checked afterwards. Outside a scope the model, effort, capacity, queue, cancellation and request fields are unchanged.

## Alternatives considered

**Change the worker to report incomplete usage.** Rejected: the worker and the adapter are outside the scope of this change and are under the upstream-edit inventory; the ledger already holds what is needed.

**Add the command, round and session as fields of an attempt.** Rejected: it changes the persisted ledger format, whose reader accepts no unknown field; the label carries them, and the event lists them with the row id.

**Treat a refused first request as a dispatch that was never admitted.** Rejected: nothing proves that the logical command was never admitted, and the case is not distinguished from a refusal that follows a settled round.

## Consequences

Under a scope a command's usage can be absent where it used to be partial. `evaluation.command.metering` is a new orchestration event type, written only in homes with a scope; the store keeps event types as text and no reader validates them; a build without this change was not run against such a home. An outcome the ledger cannot prove is now indeterminate where it was failed: a thrown failure and an error stop with an outstanding request. In the run `unknown-continuation` the members of the continuation are `indeterminate`, while the node is `failed` with `OPERATOR_STOPPED`: that comes from the existing rule that a settled result which did not complete fails the node, and was not changed. A refusal is visible in the ledger row's reason and in the rows of the metering event (`input-exhausted`, `attempts-exhausted`); the node's blocker is `OPERATOR_STOPPED`, and `ADMISSION_REFUSED` appears in no orchestration event.

## Tests

Each scenario of the `prime-rlm-evaluation` fixture starts the production Loader and daemons with only the model provider replaced, in its own home and process, and every received request is matched one to one with an admitted row by its body digest, and must already be reserved in the ledger file when it arrives. Fourteen scenarios: the original tree; `integration` (a root, two children and one batched continuation of two messages that reads a child result in its first round: eight requests, one continuation command with two rounds); `refuse-first`, `refuse-later` (the continuation's first request) and `refuse-round` (a later round of one command), each with no request sent past the refusal, no requeue, and no `RLM_DISPATCH_NOT_ADMITTED` or busy error in any event; `cancelled` (a run cancelled with a request in flight: the run is `cancelled`, the node `failed`, the request `unknown`, nothing replayed); `missing-usage`; `unknown-no-replay` (thrown), `unknown-error-finish` (an HTTP 500), `unknown-child` and `unknown-continuation`, none replayed although the retry policy lists the code; `known-retry` (a second attempt metered apart); `zero-child`; and `ordinary` (the same root without a scope: no ledger, and the model, `max_tokens` and effort the home always sent, which differ from the scope's). `evaluation-ledger.spec.ts` covers the label, the row counts and the two decisions as functions. All were run from source and from the built libraries.

Controls (one rule broken at a time, bytes restored and hashed): eleven on the ledger functions, all red, and ten on the daemon rules, eight red on the field they target (for example, without the reclassification `unknown-no-replay` retries and sends three requests, and without the withholding `missing-usage` publishes `rlm.usage` for the root). Two of the ten survived and are not covered: the status the runtime keeps for a tracked root execution is held in memory and appears in no event or record, so the mapping that makes it indeterminate cannot be observed in these scenarios; and the thrown-failure branch of the cancellation exception, because the cancelled run ends as an error stop. The order "decide, then write the event", which keeps a refused event write from turning an unknown outcome into an ordinary failure, has no test. A Resident child under a scope is covered by the existing `daemon.spec.ts`, not by a scenario.

# Agent Note: A request ledger for one evaluation scope

Status: implemented

English | [中文](2026-10-15-evaluation-request-ledger.zh.md)

## Problem

An RLM run is a tree: a root, children, grandchildren, continuations of each, and a tool loop in every one of them. Each model turn is a physical HTTP request. Before this change nothing counted those requests across the tree. The `maxDepth`, `maxChildren` and `maxTurns` limits bound the shape of the tree, not the requests; Goal accounting records usage after the fact and leaves out cache reads; the tool loop merged usage and never checked it before the next round; the worker could not set `max_tokens`, so every request carried the adapter default of 256000; and an agent-level retry policy (`maxRetries=2`) is a different thing from a worker request. A paid evaluation needs the opposite: a limit that is checked and recorded before a request leaves the process, shared by the whole tree, and honest about what it cannot know.

## Decision

**The home is the scope.** A file `evaluation-scope.json` in the daemon's root seals that home to one evaluation: scope id, the only model, an `inputBound` mode, limits for cumulative input tokens (cache reads included), cumulative billed output tokens, HTTP attempts, concurrent requests and the `max_tokens` of one request, and `thinking: enabled` with a reasoning effort. It is validated strictly at start (no default for any field) and sealed by hash into the ledger. One home is one scope, so every dispatch of that daemon shares one ledger and a retry cannot buy a fresh budget. The user's global provider, model and effort settings are not touched.

**Admission is at the physical request.** `GenerateOptions.admission` is a closure the DeepSeek adapter calls after it has serialized the body and before `fetch`, with the facts of the wire request (body bytes and sha256, model, `max_tokens`, thinking, effort, non-text content). Opting in is explicit on both sides: an adapter declares `enforcesAdmission`, and a call that sets an admission on an adapter that does not fails instead of running unmetered. The ledger checks the wire values against the scope and refuses a mismatch; it never rewrites them. The check, the reservation, and a durable write (temp file, fsync, rename, directory fsync) are one synchronous step, so concurrent requests cannot both take the last balance and a reservation is on disk before the request is sent.

**What a reservation is.** Input is the body's byte length. Output is the request's `max_tokens`. One attempt and one concurrency slot are taken. A request settles when the `usage` chunk arrives, which `translate` yields only at `[DONE]`, before the chunk is passed on; input is `inputTokens + cacheReadTokens` and output is `outputTokens` (the API's `completion_tokens` already includes reasoning, so reasoning is not added again). Everything else leaves the reservation as `unknown`: an abort, an idle timeout, an error status of any class, a stream cut before `[DONE]`, `[DONE]` without usage, a consumer that stops reading, a crash. An unknown request keeps its reservation and its concurrency slot, because it may still be running at the provider; it is never released or sent again, and only a reconciled receipt ends it. On restart every request in flight becomes unknown. Settlement is idempotent; a conflicting second settlement is an integrity fault that stops admission. Usage above its reservation is charged as reported and also stops admission: the bound or the cap did not hold, and the ledger says so instead of cutting the number.

**The input bound is audited, not proven.** The body's byte length bounds the token count only if the tokenizer is byte-level and the chat template adds no more than the JSON structure does. Neither has been shown for the provider, and the official API reference does not say in terms that `max_tokens` includes reasoning tokens. The scope therefore has to name `inputBound`. `request-bytes-audited` is the only mode that admits requests, and it is described everywhere as a byte reservation with an after-the-fact audit. `proven-token-count` asks for a bound proven before sending, which this build cannot give, so it admits nothing. No characters-divided-by-four estimate is used anywhere.

**One owner, and a ledger that is checked before it is trusted.** The ledger takes its own owner lock before it reads or writes anything. The lock file is published complete in one hard-link step, so there is no moment when it exists without its owner; a lock that is held or unreadable is never taken over, and a stale one is replaced only after the file moved aside proves to be the stale one. The daemon opens the ledger only after it holds its own lock, because the daemon lock treats a lock without a pid file as stale. The persisted file is validated before any recovery write (version, keys, states, counts, unique ids that follow the sequence, states that agree with their usage and reservations); a ledger that fails is left as it is and nothing is sent, and totals that pass the largest exact integer are refused.

**Fail closed.** Under a scope only the DeepSeek API worker may run, and Resident and remote operator dispatches are refused, so no model request leaves the daemon outside the ledger. The scope's model goes on the wire whatever the allocation chose; the `model.allocated` events still show the allocation. The three layers are counted apart: graph attempts, tool rounds (the label of each request names its command and round), and admitted or refused HTTP attempts.

## Alternatives considered

**Count in the worker only.** Rejected: a later retry or middleware could call the adapter again, and the worker does not see the serialized body. Admission sits at the fetch.

**Estimate input tokens as characters divided by four.** Rejected: it is not a bound, and a cap that cannot be exceeded has to come from a bound.

**Release the slot of an abandoned request.** Rejected: the request may still be running and billed. The cost is that one unknown request can hold the only slot of a scope with `concurrentRequests = 1` until a receipt is reconciled.

**Let the evaluation runner start the daemon with a flag instead of a file.** Rejected for now: the daemon is started by the client with fixed arguments, and a file inside the isolated home is sealed by that home.

## Consequences

Byte reservations are several times the real token count and are held until settlement, so parallel children can be refused early and every unknown request keeps its full reservation. The guarantee is exactly this: the requests of the metered API path are counted, reserved and written before they leave, with the generation values the scope names. It is not a proven token cap, not network or credential isolation (code in the REPL can still reach the network by itself), and not a wall-clock limit. No production code reconciles an unknown request yet.

Three conclusions are kept apart. (1) The generation parameters reach every physical request: the scope's model, `max_tokens`, effort and thinking mode are on the wire in each plain call and each tool round, and the fake endpoint's received bodies show it. (2) Admission is checkable: every received body joins to exactly one admitted attempt by sha256, and the ledger records what each attempt reserved and what it used. (3) A strict total token cap against the real provider is **not** established. The official Chat Completions page defines `max_tokens` as the maximum number of tokens that can be generated and lists `reasoning_tokens` inside the completion details, which supports reading reasoning as part of the completion but does not say that the limit includes it (only the Responses API says so for `max_output_tokens`, and this code does not use that endpoint). The token-usage page offers an offline tokenizer for text and says counts differ by model and that usage is authoritative; no pre-send count or upper bound for whole messages, tool schemas and results, the chat template, and the server's wrapping was found. Request bytes, text token counts, and context capacity are different facts. So `request-bytes-audited` is an audited reservation, and `proven-token-count`, which would need that proof, refuses every request; that verifies a safe refusal and does not make a formal evaluation ready to run. No endpoint is switched, no reasoning is lowered, and no budget is raised to get around this.

## Testing

`evaluation-ledger.spec.ts` covers the scope file, admission, every refusal, settlement, restart, unknown requests, the owner lock, and a table of damaged ledger files. `admission.spec.ts` runs the real adapter against a loopback server and checks the facts given to an admission, the order of settlement and yield, and every ending that must leave a reservation held. `worker-evaluation.spec.ts` checks the generation values per round. `daemon.spec.ts` runs the real daemon, worker and adapter against a loopback endpoint with a root, a child, a grandchild and a continuation, joins every received body by sha256 to one admitted attempt, and covers exhaustion, cache reads, a bound violation, a restart with an unknown request, a second daemon on the same root, and a damaged ledger. The keyless `prime-rlm-evaluation` snapshot does the same through the production Loader and daemons with only the provider replaced. Every test uses a loopback endpoint and a fake key and fails on a fetch to any other host; none can show that a real provider's token counts respect the byte reservation.

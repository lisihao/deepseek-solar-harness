# Agent Note：用户点名协作的成员

Status: implemented

[English](2026-10-09-kennel-named-members.md) | 中文

## 问题

[协作类型](2026-10-09-kennel-collaboration-kinds.md)自己选成员：辩论或评审取注册表中靠前的成员。用户只能点名一个成员。用户写“让 gamma 和 beta 评审一下”或“alpha 和 delta，辩论这个”时，没有办法表达。

## 决策

Host 在用户消息里查找已启用成员的名字，并通过 `facts.mentioned` 告诉每个类型消息提到了哪些成员，按首次出现的顺序。匹配不区分大小写；ASCII 名字不能出现在更长的单词里；较长的名字优先于它里面包含的名字；多个已启用成员共用的名字有歧义，会被略去。名字是什么意思由类型决定，`@deepseek-ai/dsh-orchestration` 中的 `kennelRoster` 是共用规则：

- 使用被点名的成员，按点名的顺序。辩论让第一个担任建议者、最后一个担任裁判，所以点名也就选了角色。
- 点名数量不足时，用注册表顺序中的其他合格成员补足，补在被点名者之后，辩论的裁判就是这样得到的。
- 被点名的成员无法参加（不合格、generation 已变）或点名数量超过协作所能容纳时，不提供候选。调度器已经告诉模型不能替换被点名的对象；提供另一个名单恰恰是替换，什么都不提供则会让 AI 去追问。
- 评审会把作者从名字中去掉：他们不能评审自己的工作。去掉后没有人被点名，就使用默认评审人，这正是作者只是作为评审对象被提到的情况。用户直接点名的成员仍然单独评审，并覆盖消息中的名字。

AI 仍然通过 id 选择候选，Host 仍然在启动前重新询问，所以被点名的名单与其他名单一样经过检查。候选 id 带有成员，所以名字解析结果不同的消息会得到不同的 id。

## 考虑过的替代方案

**让模型说出成员。** 模型只返回 id。让它返回成员，就等于让它凭空编造一个 Host 从未确认过的名单。

**为每种成员组合提供候选。** 候选数量会组合式增长，模型要在几乎一样的选项里挑。

**在界面里为类型选择参数。** 有用，但需要在输入框里加成员选择器。消息里的名字在任何客户端都可用，不需要新界面；选择器以后可以填入同样的名字。

## 后果

名字是常用词或较短的 ASCII 词的成员，可能被恰好包含它的消息误点名；影响仅限于 AI 选择了协作的消息。两个同名成员完全无法被点名。名字按用户文本匹配，不按成员的角色或头像。输入框里还没有用于协作的成员选择器。

# Agent Note：基准测试是在隔离运行上做的消融实验

Status: implemented

[English](2026-10-21-benchmark-ablation-ledger.md) | 中文

## 问题

DSH 靠插件扩展，但过去没有任何手段能说明某个插件、某种插件组合或由插件搭成的业务流，究竟是让系统变好了，还是只增加了 token 和延迟。给单一组合打一个排行榜分数回答不了这个问题，答案只能是同一批任务在不同组合之间的差异。

## 决策

一个 benchmark 就是一个实验，即套件的任务 × variant × 重复次数。variant 由 profile、有序的 `--patch` 叠加层和环境变量组成，所以“基线 + 插件 X”直接用 DSH 现有的组合机制就能表达。第一个 variant 是基线，后续分析都与它比较。

每次运行都是一个独立的 `dsh` 子进程，拥有全新的工作区、从模板 home 播种的私有 `$DSH_HOME`，以及一个私有状态目录。variant 可以通过环境变量把 home 之外的插件状态指向这个目录。如果不这样隔离，记忆类插件会把状态带到下一次重复和其他 variant 中，测出的差异就会被污染。子进程走的是真实的产品入口（`dsh --profile <profile>`），因此被测的就是实际发布的系统。

结果取自 DSH 本来就会写的会话日志。运行器通过 JSONL 持久化后端读取日志，折叠出 token、成本、轮数、步数、工具、重试，以及时间拆分：模型时间、每步最慢的工具，其余记为 harness 开销。这样不需要新的会话事件，也不需要进程内埋点，被测的运行里不含任何 benchmark 代码。

每次运行向 `runs.jsonl` 追加一条带 `formatVersion: 1` 的记录，`experiment.json` 锁定实验定义。账本同时充当实验状态：有记录的 cell 即视为已完成，因此崩溃或被取消的实验可以续跑；定义一旦改变就必须换一个新的实验 id，不能把两批数据混在一起。

新增 benchmark 的方式是写一个注册到 `ctx.benchmarks` 的套件插件。大多数套件只是声明式数据（`suite.yml`、`tasks.jsonl`、fixture），由内置评分器评分；需要自定义评分的套件注册自己的评分器。一致性工具包要求每个任务都附带一次应通过和一次应失败的运行，这样一律判通过的评分器就无法发布。

## 考虑过的替代方案

**在同一进程内运行多个 variant。** 速度更快，但插件状态、模块缓存和服务会在 variant 之间泄漏，而且按 variant 加载插件的方式会与用户实际启动时不同。

**给插件钩子埋点，统计每个插件的耗时。** 这需要在每个扩展点都加钩子，而且仍然统计不到注入上下文的插件在 prompt token 上的开销。消融差值能归因插件的全部影响，token 也包括在内。

**用数据库存结果。** 以目前的数据量，每个实验一个只追加的 JSONL 文件就够了；它不需要工具就能读，崩溃时最多损坏最后一行。

## 后果

分析（相对基线的配对差值、区间、最小可检测效应、瓶颈排名）和 Desktop 面板都直接读取账本，不触碰运行本身。多轮任务和预热会话需要在 headless driver 之外再加一个 ACP driver。`experiment.json` 不锁定 patch 文件的内容，因此在两次续跑之间修改 patch，会让同一个 variant id 下混入不同的组合。

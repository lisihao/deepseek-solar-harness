# Agent Note：狗窝评审结论生效

Status: implemented

[English](2026-10-09-kennel-review-conclusions.md) | 中文

## 问题

[评审](2026-10-09-kennel-collaboration-kinds.md)结束后只是房间里的一段文字。没有任何地方说明被评审的任务是否通过，作者也看不到意见，除非用户自己复制过去。

## 决策

评审的结论是每个评审人回复的第一行：`结论：通过` 或 `结论：需要修改`。`review` 类型在 `outcome` 中读取它，并把各评审人汇总到被评审的任务上：任一评审人要求修改，任务为 `negative`；所有评审人都通过，任务为 `positive`；评审人失败、没给出可识别的结论或还没回复时为 `unclear`（评审未结束时为 `pending`）。提示和读取使用同样的两个常量，所以不会分叉。

结论是推导出来的，不是存储的。Host 读取会话日志中本会话启动的协作，向每个类型询问根据 Run 当前结果得出的结论，房间把它显示在它所针对的任务上。存储裁决需要有人观察 Run 的完成，并会在 Run 被取消或恢复时过期；推导则会随 Run 变化。

由此产生第二个类型 `rework`。只有评审结论为 `negative` 时才提供，每次评审只提供一次，并且只提供给做这个任务的成员，在同一项目、同一模式下，且调度器仍然提供它时才可用。必须由用户要求；调度器从不自行启动。作者会收到要求修改的评审人的意见，Host 用自己的 `workGraph` 构建任务图，所以写入任务的返工与成员自己的消息使用同样的隔离和验证。该类型从不自己拼装权限。返工后的任务就是普通的已完成任务。一个任务最多交还 `maxReworks` 次，返工的返工也计入，所以评审与返工的循环会结束，最后的意见留在任务上。

`rereview` 类型补上这个闭环。返工后的任务完成后，它提供把任务交还给上一轮要求修改的同一批评审人，顺序不变，并带上要求修改的意见，让他们先核对这些意见。每个返工后的任务只提供一次，并且只有首次评审的每个评审人都仍能评审时才提供，因为换另一批人就不是“同一批评审人”；消息点名了评审人或点名某个成员时，那是普通评审。它的结论是同样的汇总，措辞为 `复审`，所以返工后的任务显示自己的结论，不通过的还可以再次返工。

为了让类型能根据历史行事，接口把调度器的工作提供项、会话中已接纳的工作任务（带上接下它的提供项，从会话日志读回）以及此前的协作及其结论交给类型。使用调度器自己的提供项，让“哪个成员能在哪种模式下接哪个任务”只有一份定义。

## 考虑过的替代方案

**重开或阻塞被评审的任务。** 评审是其他成员的建议；任务仍是原来的样子。阻塞会让评审人的文字凌驾于已经通过自身验收的任务之上。

**结论为 `negative` 时自动返工。** 这会产生没人要求的写入任务，评审与返工的循环和费用也没有上限。用户要求返工是一个选择。

**把裁决存入新的会话事件。** 它需要有人发现完成，并且重复了 Run 本身已有的内容。

**返工完成后自动启动复审。** 这是没人要求的又一批模型工作，用户也可能想换评审人；必须由用户要求。

**多数决。** 一个评审人发现了真问题，不应被多数票淹没；用户选择了保守规则。

## 后果

房间只在会话已加载时显示结论，因为它读取会话日志。由一组成员完成的任务可以评审，但不能返工。结论是文本约定：措辞不同的评审人算作不明，绝不算通过。返工后原任务同时显示评审和返工，只有对返工后任务的评审或复审才能通过它。复审需要首次评审的整批评审人；其中有人不在了，用户要求普通评审并点名评审人。真实的 Codex 和 Claude Code 回复在此尚未验证，所以它们遵守第一行约定的频率没有度量。

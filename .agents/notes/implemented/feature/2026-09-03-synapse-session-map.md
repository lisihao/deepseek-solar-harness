# Agent Note: Synapse session map as a sealed removable product plugin

Status: implemented

English | [中文](2026-09-03-synapse-session-map.zh.md)

## Problem

DSH's canonical Session Log preserves linear history and branching events, but the Desktop product did not provide a spatial view for navigating related sessions, branches, prompts, and tool activity. The upstream `dsh-synapse` project already implements this interaction as a normal DSH Web plugin, so duplicating it inside Desktop would create a second UI protocol and an unnecessary fork.

## Decision

DSH admits the upstream `dsh-synapse` v0.4.1 release as a managed, sealed, and removable product plugin. The accepted source, MIT license, release commit, and fidelity record live under `plugins/managed/synapse`; Desktop installs a reproducible local archive whose manifest maps every packaged non-generated byte back to that tracked source. The ordinary product-bundle list mounts the plugin once for both local Desktop and Product Server compositions. No DSH Core, Scheduler, TaskGraph, Physical Operator, model provider, or Agent Loop contract depends on Synapse.

Synapse remains a projection. DSH Session Log is the canonical source for session identity, history, and branches. The plugin's private `synapse/workspaces.json` stores canvas layout and a bounded content projection used by the visual map; it is not a second session authority. Removing the plugin or its private data must not remove or rewrite a DSH session.

The first integration preserves the accepted upstream runtime behavior instead of silently replacing it with a Solar-specific rewrite. Known upstream boundaries are documented: the local JSON store uses process-local advisory locking, raw workspace paths are not canonicalized with `realpath`, and the plugin does not implement multi-Server replication or a separate authentication system. Those are explicit follow-up candidates, not capabilities claimed by this release.

## Verification

The managed source checks pin the upstream release and exercise its native tests. Desktop package tests require a unique `synapse` Loader row and the `dsh-synapse` package. The vendored-input gate proves exact tracked provenance; packaged-runtime and composition gates require the Host entry, Web client entry, stylesheet, application script, patch, and package manifest to survive Electron packaging. Installed acceptance verifies the Synapse route, client module, visible session-map entry, restart persistence, and that existing Ego Lite and ChatGPT Web rows remain mounted.

## Alternatives considered

**Reimplement the canvas inside Desktop.** Rejected because it would fork the interaction model, couple the capability to Electron, and discard an already compatible DSH Web plugin.

**Modify DSH Core or the Session Log schema for Synapse.** Rejected because a visual projection does not need execution or persistence authority, and such coupling would make plugin removal unsafe.

**Follow the upstream `main` branch.** Rejected because a moving revision cannot provide reproducible Desktop packaging; v0.4.1 contains the same runtime files as the audited `main` revision and has a stable release identity.

## Consequences

Users receive a visual session and branch map without changing how DSH executes work or stores canonical history. The plugin can evolve or be removed at its capability seam. Future changes that canonicalize workspaces, replace the private store, or add remote replication require their own contract and migration decision rather than being hidden inside this import.

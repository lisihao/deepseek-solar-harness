# Agent Note：智能协作分配

状态：已实现

[English](2026-09-26-smart-collaboration-allocation.md) | 中文

## 问题

使用 API 主模型时，智能协作用文本分类器委派识别出的工作：实现类请求交给 Codex，分析类请求交给 Claude Code，模型和强度取已保存的原生配置或产品默认值。它不考虑额度、容量和模型档位，一个产品不可用时也无法改派给另一个。已有的额度感知分配器会为 TaskGraph 节点选择模型，但只在编排守护进程内运行。完成[产品模型菜单入口](2026-09-26-four-entry-model-menu.md)后，其余原生模型本就应由这类分配器按任务选择。

## 决策

resident-operators bundle 在 Host 中挂载 `@deepseek-ai/dsh-model-allocation-local`。智能协作决定委派且分配器已挂载时，`tool-physical-operator` 向它询问协作者。分类器仍决定是否委派，并提供角色（`implementation` 或 `analysis`）；分配器的领域评分把这个角色转化为对 Codex 或 Claude Code 的偏好。

报价包括可用 Codex 与 Claude Code 目录中接受 DSH 工具桥的每个原生模型，转接的 `openrouter/…` 模型除外。报价档位来自 `nativeModelTier`，它现在由 `@deepseek-ai/dsh-model-allocation` 提供，并与编排守护进程共用。Claude Code 不报告额度数据，因此这些报价放行未知额度。每个报价带有新增的可选 `rank`，即菜单的新款优先顺序，在按报价 id 排序之前用它打破同分；没有它时分配器偏好字母序靠前的 id，旧模型可能胜过新模型。请求使用 `execution` 阶段和 `quality` 目标，因为被委派的是用户的整个请求。

只有当上一次读取（包括显式菜单刷新）早于 `catalogMaxAgeMs`（默认十分钟）时，才会重新对目录做资格检查；并发的过期读取共用一次资格检查。选中的模型及其目录默认强度成为 Resident profile，路由决策的 reason 写明报价、强度和分配器理由。分配器缺失、目录读取失败或没有合格报价时，回退到分类器选出的算子，并在 reason 中写明原因。

## 备选方案

**每次委派都实时读取目录。** 额度总是最新，但每次委派都要等待所有原生 CLI 完成资格检查。

**只用上一次手动刷新的目录。** 不增加延迟，但额度可能任意陈旧。

**只在固定时才放行 Claude Code。** 这是 TaskGraph 对未知额度的规则。它能保护 Claude 额度，但会把分析类请求交给 Codex，所有者否决了这种做法。

**只提供菜单中的最新模型。** 对完整目录排名，可以让较旧、较快的模型继续供之后的目标与强度规则使用。

## 后果

- 智能协作现在会选择对应产品中最新的高档模型，某个目录不可用或额度耗尽时改派给另一个产品。
- 自动委派时，Claude Code 的用量没有额度保留保护。
- 每次委派仍使用所选模型在目录中的默认强度；任务复杂度、重试和推理强度规则仍是提案。
- 固定协作者、显式点名算子和物理主模型的路由保持不变。

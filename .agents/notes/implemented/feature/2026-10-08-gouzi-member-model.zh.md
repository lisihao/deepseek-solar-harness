# Agent Note：为每只狗子固定一个模型

Status: implemented

[English](2026-10-08-gouzi-member-model.md) | 中文

## 问题

狗窝的每个任务只写明成员的算子，模型由调度器的 Smart Auto 每次自行选择，用户无法让某只狗子固定使用某个模型。一个成员同时有 Codex 和 Claude Code 两个运行环境，它们的目录提供不同的模型 id，所以任何设置都必须同时决定由哪个运行环境执行。

## 决定

[成员](../../../../packages/orchestration/orchestration/src/gouzi.ts)带一个可选的 `model`：取自运行环境目录的一个原生产品模型 id。缺省表示由 Smart Auto 选择，与此前相同。这个 id 同时决定运行环境，因为只有目录中列出它的算子才能执行任务，所以设置不需要按运行环境分别记录。

[注册表](../../../../packages/orchestration/orchestration-local/README.md)把它存在 state schema 6 新增的可空列 `gouzi_members.model` 中。创建与 `gouzi.edit` 接受去除首尾空白后 1 到 128 个可打印字符的 id，`edit` 传 `null` 则清除。省略 `model` 的编辑保留原值，模型变化不会提升角色版本或成员 generation。

[调度器](../../../../packages/orchestration/ui-gouzi/README.md)只通过目录包含该模型的可用算子提供已固定的成员，没有可用算子的成员不是候选。候选带有该模型，任务节点写入 `operator.profile.model`；启动前的复核在决定之后成员的模型变化、或某个算子不再提供该模型时拒绝运行。

编辑表单通过 `models` 操作列出成员可用运行环境的模型，打开表单时才请求，因为名册轮询不应查询运行环境目录。已固定但没有任何运行环境提供的模型仍可选中，并标为不可用。领养时不设置模型，因为新成员启动之前没有运行环境目录可供选择。

## 考虑过的替代方案

**按运行环境分别设置模型。** 以 Codex 和 Claude Code 为键的映射能让一只狗子持有两个模型，但节点只带一个 profile，而模型 id 已经决定运行环境，映射会增加一个可能自相矛盾的状态。

**把选择放在 Desktop 目录里。** 调度器和注册表已经拥有成员身份与 generation。再加一个存储，会让从未同意过该模型的重建成员继承它。

**不加 schema 版本，直接加列。** 新增的可空列在旧程序里也能打开，但旧程序随后写入的成员会丢失该设置。已发布的状态要求明确的带版本失败，所以 schema 6 让旧程序拒绝打开该数据库。

## 后果

schema 6 迁移是单向的，与 schema 5 相同。运行环境下线了已固定的模型后，这只狗子会在调度中静默失去资格，直到用户修改设置，房间里也看不到它的候选。固定只作用于狗窝调度；用户通过其他路径把任务发给狗子算子时仍由 Smart Auto 选择。在真实的 Codex 或 Claude Code 目录上的已安装产品行为尚未在此验证，也不意味着已部署。

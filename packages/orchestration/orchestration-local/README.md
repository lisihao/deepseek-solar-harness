# Local Orchestration

English | [中文](README.zh.md)

This package provides `ctx.orchestrations` through an independent `dsh-orchestratord`. The disposable DSH plugin is a Unix-socket client; the daemon is the only SQLite writer and keeps accepted TaskGraphs running across DSH or Desktop restarts.

Packaged Desktop assigns `desktop-<SemVer>` as the local daemon build identity. The strict handshake rejects a daemon from another application build, asks it to shut down, preserves its SQLite state and artifacts, and then starts the installed build. Source development keeps the explicit `development` identity unless `DSH_BUILD_COMMIT` is supplied.

The daemon hosts the deterministic direct Intent Provider, basic Context Provider, owner-local content-addressed Capsule Registry, quota-aware model allocator, persistent Continuous Harness Provider, graph validator, conflict-aware Scheduler, immutable ExecutionPlan compiler, and a private physical-operator composition that dispatches Resident Claude Code or Codex turns. State lives under `<DSH_HOME>/orchestrations`; the socket is owner-only and the database uses WAL.

The Scheduler starts independent nodes up to the Graph's `maxParallel` bound without a phase-wide barrier. Dependencies, overlapping write/effect scopes, and the worker bound serialize only affected nodes; each wait reason is persisted with the run. Every attempt receives the built-in `context.clean-task` instruction Capsule and a fresh Resident lane, so a reused Codex or Claude Code host does not inherit an earlier native thread or fork the parent conversation history.

The allocator treats every reported allowance window as a simultaneous constraint, prioritizes qualified native-subscription pools, and uses metered API capacity only when the selected objective permits it. Its live capacity recommendation lowers the Scheduler ceiling below `maxParallel`; temporarily busy subscription capacity waits instead of silently spending paid API budget. Near-reset allowance is preferred while it remains usable. Node-declared fallback operators are resolved from the same live catalogs only after the preferred operator fails availability, authentication, model, or quota qualification; the sealed allocation artifact and event retain the requested operator/model and reason code.

An optional versioned `cluster.json` owns both fixed Product Server membership and remote Resident capacity. A member with `remoteExecution.enabled` is projected through the same physical-operator seam as `remote.<member>.<operator>`; its repository allowlist maps credential-free `host/path` identities to Server-local checkout paths or Git URLs. Qualification failure on one member marks only that member unavailable and does not block healthy local or remote Providers. The legacy `remote-operators.json` remains readable only when no cluster member defines `remoteExecution`; defining both catalogs is rejected so capacity cannot drift away from election membership.

Each ordinary remote attempt derives repository identity, exact HEAD, and optional subdirectory from the sender's clean Git workspace. The receiving Server keeps immutable Git objects under `<DSH_HOME>/orchestrations/remote-workspaces/cache` and gives every execution id its own leased writable checkout under `executions`; parallel attempts at the same commit therefore cannot observe each other's tracked or untracked edits. Terminal inspection removes a settled checkout, while running or indeterminate receipts renew it and expired leases are reaped. The Server never interprets the sender's absolute path. An oversized Resident result is fetched by its remote `sha256:` reference under explicit byte/time bounds, verified over the exact JSON bytes, validated as a complete product-neutral result, then persisted and read back through the scheduling leader's local Orchestration CAS. Inline and transferred results retain the original execution id, durable command Receipt, Server affinity, and generation fencing.

TaskGraph node prompts label the context path `Sender workspace` and instruct native executors to resolve filesystem operations and relative scopes against their current working directory. This does not alter the listed permissions or task acceptance. The receiving Host supplies its exact checkout identity through the [Remote Sync execution context](../../client/connection/README.md#remote-sync-and-stable-session-handoff); the [Agent Note](../../../.agents/notes/implemented/bug-fix/2026-10-04-remote-native-workspace-context.md) records why sender text is preserved.

Remote HTTP 5xx responses retain at most 500 characters of the response body in the transport diagnostic, or an explicit unavailable-body fallback. They remain `TransportError` and produce `COMMAND_INDETERMINATE`: the response does not establish whether admission or native execution occurred. Reconcile the existing command before any explicit retry; neither body text nor status alone is classified as a native refusal.

The same `cluster.json` gives those members one TaskGraph authority. Each member persists its own term, vote, leader lease, and replicated logical orchestration state. Campaign and renewal use one in-flight operation per kind plus an election epoch fence, so a higher-term heartbeat cannot be overwritten by a late vote or replica response. A node may mutate Scheduler state only while it holds a non-expired majority lease. Before any sealed attempt reaches a Resident or model-worker Provider, the leader renews that lease and brings enough followers to its current `commitIndex`; only then can the external product call begin. A follower never replays an accepted command and rejects stale-term replicas. Desktop descriptions expose only the bounded leader projection required for multi-Server ingress selection; vote, heartbeat, export, and install remain admin-only Remote Sync operations.

Every member must use the same `cluster.json` membership and reach its peers through authenticated loopback tunnels. First release replication sends a complete logical snapshot, verifies every content-addressed artifact digest, and installs it transactionally while preserving the receiver's local election identity. The full snapshot is intentionally bounded by the Remote Sync request limit; incremental state transfer is deferred for very large orchestration stores.

For Resident RLM, the sealed ExecutionPlan contains a high-tier root allocation and a subscription-first low-tier default child allocation. The root model uses the persistent `typescript_repl` namespace to inspect programmable context, admit asynchronous recursive children, receive explicit family messages, and continue durable goals or heartbeats. The model chooses the child topology at runtime; DSH only enforces `maxDepth`, `maxChildren`, `maxTurns`, Graph parallelism, and provider capacity. Every child and continuation has a stable Receipt and a content-addressed result artifact. The composite occupies one global Scheduler slot, so node-local recursion cannot become a competing TaskGraph or oversubscribe concurrent DAG work. Every API (model-worker) child or continuation of an attempt runs under its own cancellation. The first execution of a child follows the execution of the session that spawned it; a later turn of a session (a continuation) follows only the attempt, so an interrupted earlier turn does not cancel it. Interrupting a session stops the active executions of that session and of what it spawned, never the root or a sibling. Deleting a child also closes its subtree for good ([rlm-runtime-local](../rlm-runtime-local/README.md)), and cancelling the run or the root still reaches every execution at least once; an execution refused after a delete was already interrupted once and is reached again through the attempt signal its start received, which has no dynamic test for a Resident turn. The last continuation the runtime drains keeps its own stop reason (`error`, `aborted`, `max-tokens`, `refusal`) and any partial output: a continuation that failed or became indeterminate fails the node and the run instead of being reported as `completed`, whether it returned output or not. The root's own result counts as the last drained result when no continuation ran, so a root that ends in `max-tokens` or `refusal` fails the node and the run. A result that is not `completed` ends the execution: an active goal does not start its next turn after it, and Autonomous Mode does not start another round after a root that stopped with `max-tokens` or `refusal`; `error` and `aborted` still fail the node by throwing. The goal stays active and no recovery policy exists, so resuming it is an explicit decision. A child that merely fails without a root continuation failing does not fail the graph. Interrupting a later turn of a child has no dynamic test yet.

A message continuation of an RLM session is dispatched in one place, so the prompt built in `rlm-continuation.ts` is shared by the API (model-worker) and Resident paths. An API continuation is a new request whose messages hold no earlier turn of the session; a Resident continuation resumes the native session of the same lane, so its native context may hold earlier turns. In both, the prompt restates what the host knows and does not replay the history. It carries the queued message; the session's own task, whole (the task text the session was created with, which is not necessarily the first prompt it received); the names saved by the last successful cell and the names whose save degraded in it, as two lists of at most 64 names each with the rest counted; the parent, siblings, and direct children the session can already message, each with the state of its REPL (`running`, `idle`, or `inactive`), which does not say whether that agent finished its task or reported; and the rules to reuse an existing top-level name instead of declaring it again and not to read the delivered message again. The added facts never copy a variable value, another agent's task, or message text (the prompt itself carries the current message). The node result is still the output of the last continuation the runtime drained. For a message from another agent the text says the last reply must follow the task's output format; for controller input, as the runtime recorded it (`messageOrigin`, never the message text), it says the input may change the task or its output format and the task applies otherwise. Controller input of an earlier turn is not restated. The text does not choose which output counts. Goal, heartbeat, and Autonomous continuation prompts are unchanged.

Prime-compatible Autonomous Mode is an optional policy around that same sealed RLM lane. After each settled root or continuation turn, the daemon durably accounts non-cached input, output, and cache-write tokens, evaluates host quality gates before limits, and either reuses the same native Session for one bounded continuation or settles with an explicit reason. A passing gate is the only successful terminal condition when gates are configured; exhausting continuations, turns, tokens, elapsed time, or gate retries never becomes apparent success. Failed unchanged work consumes another retry without rerunning the command. Gate children inherit the shared credential-scrubbed environment, are tree-terminated on timeout or cancellation, and reach process quiescence before the attempt continues. This loop persists in the orchestration database and remains subordinate to the one TaskGraph Scheduler.

Prime-compatible automatic refinement is root-only and runs at a real turn boundary after 25 assistant turns or a recorded compaction checkpoint, with a 20-minute cooldown. A native-subscription model first reviews whether a durable lesson exists and only then plans independently applicable Harness edits. Failed or crash-uncertain review phases are not replayed automatically, and the background path does not silently fall back to a metered API. Executable TypeScript Skills are resolved from managed aliases to trusted `skillProviderModules`; model-supplied package paths are never imported.

An automatic retry creates a new attempt only when the node policy names the returned error code and still has attempt budget. Resident response-stream disconnects arrive as retryable `RUNTIME_UNAVAILABLE`; an explicit native-product allowance failure arrives as `QUOTA_EXHAUSTED`. A permitted quota retry excludes the exhausted quota pool (or the exact offer when no pool identity exists) before resealing the next attempt. Malformed results and indeterminate commands are never replayed automatically. Graceful daemon shutdown first blocks new Scheduler ticks and awaits the in-flight tick before disposing state; detached tick failures are logged and persisted as a bounded `scheduler-fatal.json` diagnostic. It then ends accepted control connections before reporting closure, so a retiring build cannot remain alive behind a non-accepting socket.

While an attempt runs, the daemon copies bounded Resident progress phases into the orchestration event stream. Settlement keeps the complete operator result in its Evidence artifact and adds a bounded user-facing output preview to the terminal event; the preview leaves out the operator's reasoning blocks, which stay only in the Evidence artifact. Protocol version 7 includes digest-verified `artifact.read`, durable Autonomous state, and the term-fenced cluster control methods, so an authenticated projection can load a retained Evidence result on demand without copying prompts, private reasoning, terminal screens, or product-local transcripts into the event stream.

Schema 5 adds `gouzi_hosts` and `gouzi_members`, written only through `OrchestrationStore.gouzi` (`GouziRegistry`). A host row holds the authority epoch it accepts and the name of the credential entry; the credential itself is never stored in SQLite. A member row holds the endpoint its process listens on, because several members on one host listen on different ports; `setEndpoint` replaces it each time the process starts, and a member with no endpoint is not registered as an operator. A member starts in `provisioning`, moves through `enabled` and `retiring`, and leaves the count of ten only by `archive`, which needs revoked credentials, settled work, and a stopped process tree. `connection` and `activity` are stored beside `membership` and change independently. Creation is one immediate transaction that counts every non-archived member, so the eleventh create fails with `GOUZI_LIMIT_REACHED`. The two tables are not part of the cluster replica; a promoted follower pairs its hosts again. A member row also holds an optional `model`, a native product model id that `gouzi.edit` sets or clears with `null`. Schema 7 adds an optional `profile` (the notes the user wrote for the member, 1 to 2000 characters without control characters; `gouzi.edit` sets it or clears it with `null`). Schemas 5, 6, and 7 are one-way migrations: an older program refuses the database. Before the first migration to schema 7 the store copies `state.sqlite` to `state.sqlite.before-schema-7` (mode `0600`) and never overwrites that copy, so a manual rollback restores the file from before the migration. The copy is one SQLite snapshot written by `VACUUM INTO`, so it holds every commit still in the write-ahead log even while another connection holds an older read, and it is checked (integrity and schema version) and renamed into place, so the final name never holds a partial copy. A copy that cannot be made or checked stops the start before anything is migrated.

`gouziOperatorServer` projects a registered, enabled member as a remote Server whose operators are addressed `gouzi.<gouziId>.<operatorId>`. For every attempt it reads the member, its host, and the attempt's sealed node execution plan, and signs a `GouziExecutionGrant`: run, node, attempt, execution id, generation, authority epoch, read, write, and effect scopes from the plan, a deadline, and a `planHash` equal to `gouziRequestHash` of the request it then posts. It refuses a member that is not `enabled` and any execution id that is not a top-level TaskGraph attempt, so a member never runs RLM children or Auto-Refine stages. When the run's admission names `gouziRecipient` or `gouziRecipients`, it also refuses a member that no recipient names and a member whose generation or execution entry differs from its own recipient; a recipient set binds each member separately. The first version does not run without the main instance reachable, so `offlineUntil` equals `deadline`; the deadline is the member's own `grantDeadlineMs` (60 seconds to 24 hours, set at creation). Every remote refresh the daemon registers each `enabled` member, reading the host credential from `ctx.credentials` under the host's `credentialRef` (a loopback or tunnel endpoint needs none), and records `connection` as `online` or `unreachable` and `activity` as `working` while one of the member's attempts is accepted or running.

The daemon asks each registered, enabled member's Server who it is (`gouzi.hello`, an in-memory answer) on every remote-operator refresh, and records the member `unreachable` after two consecutive missed answers (a 2 s timeout each) and `online` again on the next answer; its operators stay registered and report their own availability. Without this probe a member whose worker had stopped stayed `online`, so the panel never offered to wake it.

`GouziControl.executionOperators()` uses the read-only protocol-7 `gouzi.execution_operators` query. It joins enabled registry members to actual remote registrations only when member identity, generation, host, owner, and endpoint still match, then reads fresh Resident catalogs for full operator ids, availability, reasons, models, and the model the catalog marks as default. The query also returns `projectScopes` from the matching fresh Resident catalog's `gouziWorkspace`: only the persisted default project resolved and verified by `registeredDirectory` contributes its member-local real path. For a non-local member's read-only shared-project graph, this authenticated catalog path belongs to the receiving host; compilation does not require the same path to resolve with `realpath` on the scheduling Mac. Missing fields from older endpoints produce `[]`; generic, mismatched-generation, or unreachable registrations provide no directory authority. Missing or stale registrations yield an empty operator list; `connection: online` alone never implies an available executor. The query starts no member and changes no membership, grant, or scheduling state. The [Gouzi room](../ui-gouzi/README.md) consumes this data for display and addressed standard TaskGraph admission. Compilation and start validate `admission.gouziRecipient` against the current directory: every node must use only its admitted operator ids, with no fallback, RLM, or Autonomous Mode. Unavailable or changed recipient generations fail instead of being rerouted.

The `./remote-host` entry mounts only the remote execution host service, so a Gouzi member can execute in its registered directory without a TaskGraph daemon, scheduler, or cluster election. Its persisted `remoteExecution.projects` maps opaque project ids to exact selected Server-local directories, and `defaultProjectId` selects the initial project. The `gouzi-project` workspace identity sends a project id rather than a sender path or invented commit; optional origin metadata does not grant directory access. Execution requires the mounted member service and a grant matching member identity, generation, and request hash. Direct directory execution preserves untracked files, unborn repositories, and repositories without origin. Shared directory locks and execution receipts live outside the selected projects; settlement releases execution metadata without deleting project files. Conflicting or unresolved commands block reuse, and unknown outcomes are not automatically retried. See the [directory adoption decision](../../../.agents/notes/implemented/feature/2026-10-06-gouzi-directory-adoption.md).

A Gouzi member with registered projects uses its persisted default project and exact selected real directory. A member configured only with repositories uses clean exact-commit Git materialization; grant and member-generation checks apply to both modes. Directory qualification checks configuration and directory availability, not whether the directory is currently busy. Durable lease inspection is read-only; a known Native receipt permits recovery of the original turn, while a lease without a Native receipt remains indeterminate. Directory locks are released only on a proven settlement or a correlated command refusal followed by a successful absent-receipt query; unresolved outcomes keep their locks without replay.

## Directory snapshot delivery

`workspaceIsolation: directory-snapshot` captures plain, unborn, or dirty directories into a task-owned Git checkpoint, excluding `.git` and preserving the original index and HEAD. For Gouzi writes, admission requires registered `hostId: local` and a loopback endpoint; remote full-snapshot transfer is not authorized by this route. The receiving executor must freshly attest generation limits, governed file policy, and workspace-mutation return. Work executes after approval in an isolated checkout; independent verification receives a bundle of the current modifications, not just the original base.

New private checkpoint repositories and bundle-receiving repositories persist `core.autocrlf=false` and `.git/info/attributes` containing `* -text -eol -filter -ident -working-tree-encoding` after initialization, so capture, checkout, and linked actor worktrees preserve file bytes instead of applying line-ending, filter, ident, or encoding transformations. Snapshot mutation diffs use `--no-textconv`. These settings belong to task-owned Git metadata; they do not modify the source `.git`, index, HEAD, or user `.gitattributes`. Existing receipts retain their original snapshot, and unresolved snapshot or receiving-workspace identities are not automatically rebuilt.

The verification node's `model-verdict` requires strict JSON with `accepted`, a nonempty `reason`, and nonempty string `evidence` entries. Negative or missing verdicts, malformed fields, and absent evidence block source application. Generic file tests exercise permission and mutation mechanics; they do not establish the verifier's semantic judgment quality. Final application checks affected source paths and their parents against the checkpoint before changing files. Delivery persists `applying` before source mutation and rejects pause/cancel in that critical phase; cancellation accepted earlier prevents application. An unknown delivery becomes indeterminate and requires reconciliation of the original effect.

## Evaluation scope

A file `evaluation-scope.json` in the daemon's root (inside its DSH home, never in the global configuration) seals that home to one evaluation. It is read and validated when the daemon starts, with no default for any field, and a file that cannot be used stops the daemon. It names a scope id, the only model, an `inputBound` mode, the limits (cumulative input tokens including cache reads, cumulative billed output tokens including reasoning, physical HTTP attempts, concurrent requests, and the `max_tokens` ceiling of one request), and `thinking: enabled` with a reasoning effort. One home is one scope, so the root, every descendant, every continuation, every tool round and every node retry draw on the same ledger `evaluation-ledger.json`; a retry never gets a fresh budget, and a ledger written under a different scope file is refused.

Under a scope the daemon sends the scope's model, ceiling and effort on every API worker request, and each physical request is admitted by the ledger after its body is serialized and before it is sent. Admission is one synchronous step: it checks the balance, records the reservation on disk (written, fsynced, renamed), and only then lets the request go. It reserves the request body's byte length as input, the body's `max_tokens` as output, one attempt, and one concurrency slot, and it refuses a request whose wire `max_tokens`, thinking mode, effort or model differ from the scope, that carries non-text content, or that does not fit. Settlement happens when the provider's usage arrives (cache reads count as input; `completion_tokens` already includes reasoning); it replaces the reservation, is idempotent, and a conflicting second settlement stops all admission. A request that ends without usage (abort, error, a stream cut before `[DONE]`, a consumer that stops reading, a crash, a restart) stays `unknown`: its reservation and its concurrency slot stay held, it is never released or sent again, and only a reconciled receipt ends it. Usage above a reservation is charged as reported, never cut, and stops all later admission. The graph attempts, the worker's tool rounds, and the admitted and refused HTTP attempts are separate counts: the ledger records each HTTP attempt with its command and round label.

The ledger has one owner. Opening it first takes an owner lock that is published whole in one step, so there is no moment at which the lock exists without naming its owner; a lock that is held, or cannot be read, is never taken over, and one whose owner has exited is replaced only after the file moved aside proves to be the stale one. The ledger is created, recovered, or written only after the daemon lock is held. A ledger file is validated before anything is rewritten (version, keys, states, counts, unique ids that follow the sequence, states that agree with their usage); a ledger that fails is left as it is and nothing is sent, and totals that pass the largest exact integer are refused.

A scope meters API worker requests only. Under it the daemon refuses any other worker and every Resident or remote operator dispatch, so no model request leaves the daemon outside the ledger. The model named in the scope is sent on the wire whatever tier the allocation chose; the run's `model.allocated` events still show the allocation.

`inputBound` says how input tokens are bounded before sending. `request-bytes-audited` reserves the body's byte length and audits it against the usage the provider reports afterwards. It is not a proof: the byte length bounds the token count only if the tokenizer is byte-level and the chat template adds no more than the JSON structure does, and a request that exceeds its reservation is detected only after it was sent. `proven-token-count` asks for a bound proven before sending; this build has none, so a scope that asks for it admits nothing. That refusal is tested as a safe refusal; it does not make a formal evaluation ready to run. The official Chat Completions page defines `max_tokens` as the maximum number of generated tokens and lists reasoning tokens inside the completion details, but does not state that the limit includes them, and no pre-send count of a whole request was found.

## Model Experience

Indirectly, through `@deepseek-ai/dsh-tool-orchestration` and physical operators that consume the sealed TaskGraph node prompt documented above.

#### KV Cache effect

Each attempt receives one sealed Context Packet. Later graph, capsule, or capability generations produce a new packet instead of mutating a cached request. A message continuation is its own request. Its prompt adds the session's whole task, up to 64 saved and 64 degraded variable names, and one line per visible agent to the queued message, so its input grows with the task length. How much of it the provider's cache reuses, and whether the added input is repaid by fewer cells, is measured by an experiment, not established by the unit and snapshot tests.

## Known Limitations and Deferred Work

- Under an evaluation scope the wire model is the scope's, but the run's `model.allocated` events and the usage events (`rlm.usage`) still name the model the allocation chose. Compute cost from the ledger, not from those events.
- No production code reconciles an `unknown` request yet, so one that ended without usage keeps its reservation and its concurrency slot until the home is replaced; with `concurrentRequests = 1` that blocks every later request.
- An evaluation scope bounds the requests of the API worker. It does not isolate network access or credentials, so it does not stop code in the REPL from reaching the network on its own; it sets no wall-clock limit; and its input reservation is the request body's byte length, audited after the fact, not a bound proven before sending.

- The names and agent states in a message continuation prompt are a host snapshot: they leave out names declared by failed cells and properties set on `globalThis`, and an agent's REPL state says nothing about its progress. The prompt does not make a model follow the output format; the tests prove what the model is given and which output the node keeps.
- TaskGraph admission rejects `rlm=disabled` with `autonomous=enabled` before compilation artifacts are written. Legacy persisted preferences remain readable and fail only when used for a new admission.

- Baseline capsule bindings support instruction and read-only resource/data references. Tool, MCP, secret, and executable Guard bindings fail closed until a Provider implements their enforcement.
- Claude Code and Codex support pre-dispatch and next-turn injection only; immediate in-turn checkpoint updates return `CAPABILITY_HOTSWAP_UNSUPPORTED`.
- RLM performs bounded recursion inside one sealed node. It is an execution strategy, not another product or global Scheduler; a crash without a provable composite terminal result becomes indeterminate and is never replayed automatically.
- Autonomous Mode is opt-in and currently uses host shell quality gates; it does not infer a task-specific end condition when no gate is configured.
- The base bundle contains no production Skill catalog. Deployments install trusted Skill Provider plugins explicitly; a managed entry whose Provider is absent remains visible but unavailable.
- Ordinary remote Git materialization requires a clean committed Git workspace with a configured origin and an allowlisted source containing the locked commit on every execution Server. Uncommitted sender changes, credential transfer, arbitrary absolute-path mapping, and mutable shared worktrees are deliberately unsupported.
- Cluster membership is fixed configuration in the first release. Membership changes and incremental replicas require an explicit future protocol revision; a two-member cluster cannot continue scheduling after either member fails because it no longer has a majority.

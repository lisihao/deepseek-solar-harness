# @deepseek-ai/dsh-ui-gouzi

English | [中文](README.zh.md)

The Gouzi surfaces for the browser. Day to day the user meets the **kennel**: a sidebar row that shows the dogs' faces and how many are awake, and opens (or creates) one chat session composed from the `kennel` agent preset, where a Host-owned AI dispatcher selects one qualified dog for each real user message. Configuration lives in Settings: a **狗子** page lists the long-lived execution members of this main instance and holds the controls to adopt, edit, wake, rest, and retire them. The Host half serves `/api/gouzi` on the same origin as the Web UI; the browser half draws six inline SVG avatars and a five-step adoption wizard (avatar, name, home, role and projects, confirmation). The home step picks the machine the member lives on: this machine, an SSH machine added earlier, or a new one (address, port, user, password). The project step never asks for a typed path: it lists the user's most recently used workspaces as checkboxes (a verified usable recent workspace preselected) and a button that opens the Host's native folder picker; the chosen absolute paths go to `/api/gouzi` as `projects`. On an SSH machine the step browses and checks existing directories on that machine instead.

Opening the kennel keeps the selected workspace and uses a separate chat: it resolves the current session's workspace membership first, otherwise a valid recent workspace or the newest known workspace. It reuses only the latest unarchived `kennel` session belonging to that workspace, preserving each workspace's kennel history separately. If none exists, it awaits the existing [workspace-scoped `sessions.create({ workspaceId })`](../../client/runtime/README.md#new-session-and-the-blank-mirror) operation, applies the preset to that exact created session, records its preset, and then opens it. No workspace reselection is required. Missing workspace, creation failure, or preset rejection reports an error and leaves the original chat selected; rejected composition may leave an ordinary blank session, which is not automatically deleted. The [workspace navigation decision](../../../.agents/notes/implemented/bug-fix/2026-10-04-kennel-workspace-navigation.md) explains why creation does not watch the global current session.

The kennel chat uses a dedicated room with a persistent member and task panel on the right. Its message area owns an independent scrollport, while `conversation.room.composer` renders a separate input area sharing the room’s draft and recipient state. The conversation Root retains the sole mandatory `conversation.composer` chain for Question, PlanReview, Approval, and Readonly interactions. When the session is inert or model-blocked, the room composer declines and the existing InputBar remains available with its unblock controls. A TaskGraph `awaiting_approval` state alone does not create a pending session interaction. Clicking a member name selects its identity and generation as the send target; clearing it restores automatic dispatch. “查看消息” controls independently filter displayed records and never change the send target. The room displays real user messages, actual errors with their message and code, and attributed task results; context and internal dispatch records remain hidden. Typed `@name` text alone does not select a recipient. Sending and older-history reads use the room’s explicit session-scoped conversation service, independently of the globally selected chat. An unavailable session or conversation service rejects the operation. The browser preserves the draft and selected target on send failure; a stale room read, changed generation, disabled member, or lack of an available execution entry blocks an addressed send instead of switching recipients.

`GET /api/gouzi?session_id=<session>` returns `GouziRoomSnapshotV1` with the authorized dashboard, current registered execution entries, and only runs whose `admission.sourceSessionId` equals that session. Runs without admission are excluded even when they share a workspace. A task result requires a terminal `node.evidence.accepted` or `node.failed` event for the node’s current attempt and capability generation, a retained evidence reference, and an operator matching the exact attempt’s sealed execution plan. If the run’s durable `admission.gouziRecipient.operatorIds` contains the sealed operator, attribution keeps that admission’s original `gouziId` even after the member changes generation or retires. Without that binding, only a unique current actual registration associates the operator with a member; otherwise the result shows its actual operator id. Results carry the authoritative `OrchestrationEvent.time` and merge with session messages by their recorded times rather than by polling arrival. Missing or mismatched fields leave the result absent, and unknown scheduler states remain visible. `GET /api/gouzi?session_id=<session>&run_id=<run>&evidence_ref=<ref>` returns the actual retained evidence artifact only when the run belongs to that session and a node retains the reference; other references return 404. These authenticated reads preserve existing device scopes and do not dispatch work.

With `dispatcher.enabled`, each real user message is logged before the auxiliary model call. The Host derives candidates only from enabled members with current execution entries and verified default-project directories. Each candidate fixes member identity, generation, project, operator ids, and `chat`, `read`, or `write` mode; the model returns only a supplied `candidateId` or `clarify`. Candidates also include inspect, pause, resume, and cancel actions for existing runs admitted by this exact source session, bound to their current revision. Control selection never creates replacement work; indeterminate runs allow inspection only. Explicit recipients restrict these candidates. Plugin, context, and tool messages cannot initiate automatic dispatch or replace a human-selected recipient. The Host rechecks the selected candidate before compilation and start, disables RLM and Autonomous Mode, and supplies no fallback operators. Missing projects or executors, changed targets, invalid JSON decisions, and clarification requests fail explicitly without choosing another dog.

An ordinary greeting starts an actual member TaskGraph in `chat` mode with no filesystem or effect permissions. `read` allows read scopes; `write` uses high risk and required independent verification through the existing approval and TaskGraph lifecycle. These bounded graphs do not grant command or network effects. The durable decision is a selection record, and successful message submission is not execution acceptance. Submission records a stable command identity before start; an unknown start outcome must be reconciled against the original command rather than redispatched. Outputs remain labelled “任务结果”. The [AI dispatch decision](../../../.agents/notes/implemented/feature/2026-10-07-kennel-ai-dispatch.md) owns the selection and execution separation.

File tasks require fresh catalogs explicitly supporting generation limits and the governed workspace policy; absent capabilities are rejected. Read/write tools provide only bounded list, read, search, write, and remove operations under resolved scopes and forbidden-path checks, with symlinks refused and no shell or network tools. For non-local read-only shared-project work, the verified project path comes from the receiving host's actual catalog and need not exist on the scheduling Mac. Writes currently require a registered `hostId: local` member and a loopback endpoint: full directory-snapshot transfer to another host is outside this route. After approval, work mutates an owned checkpoint, and independent verification reads the current modified bundle. Negative, missing, malformed, or unevidenced `model-verdict` results prevent applying changes to the source. See [snapshot delivery](../orchestration-local/README.md#directory-snapshot-delivery).

Every model request, task start, and run-control effect requires session flush to return `true` first; persistence failure stops the external action. Unknown effects are reconciled against their existing identities, never replayed automatically.

The invariant companion checks prior committed records in the same Session before append commits: a request requires a real user message, a submission requires a selected work candidate after its request, admission requires a prior submission, and control must match its selected candidate and result run; it rejects orphaned or mismatched records without observing flush or proving persistence.

`GET /api/gouzi` returns `GouziDashboardV1`: the limit of ten, how many members hold a slot, whether this caller may manage, whether this Host can start members, and every member that is not archived. Each member carries `membership`, `connection`, and `activity` plus one `state` reduced by `gouziPrimaryState`: a member outside `enabled` shows its membership, an unreachable member shows that before its last activity, and otherwise the activity shows. `POST` takes a `GouziControlRequest` and requires the `x-dsh-gouzi-control: 1` header; a loopback owner, `cockpit`, and `admin` devices may manage, while `pocket` devices only read and a `gouzi` credential is refused.

A member can be pinned to one native model. The edit form offers the models returned by the `models` action, which lists the catalogs of the member's currently available runtimes without repeats and returns an empty list while the member is offline; a pinned model that no runtime offers stays selectable and is marked unavailable. `edit` sets `model` or clears it with `null`. The dispatcher offers a pinned member only through runtimes whose catalog carries that model, writes it to the task node's `operator.profile`, and refuses to start when the member's model changed after the dispatch decision. A pinned model that no available runtime offers leaves the member out of the candidates, and an unpinned member leaves the choice to Smart Auto.

`check-projects` accepts `hostId` and a nonempty list of absolute `projects`, inspects existing directories without changing them, pairing hosts, or creating members, and returns `GouziProjectsCheck`: each requested `path` has `usable: true`, or `usable: false` with a `message`. Git repositories, repositories without origin, and ordinary directories are accepted. The picker checks suggestions and newly selected folders before enabling selection; Next requires every selected project to have passed. Pending checks and failed requests cannot authorize a selection. Missing paths, files, and permission refusals produce actionable directory errors; process and timeout failures remain failed requests. Closing the wizard before confirmation does not initialize Git.

Confirmed adoption repeats read-only inspection of every selected directory and checks the ten-member capacity before calling `prepareRepository` sequentially for each distinct resolved source. Preparation initializes Git only when the selected directory is outside a Git repository; it does not stage files, commit, or change origin. `GouziProjectSource` contains an opaque SHA-256 `projectId`, the exact selected real directory `source`, and optional canonical origin metadata `repository`. The first selected project is shown as the default in confirmation and persists as `defaultProjectId`. A preparation failure creates no member or host pairing and consumes no slot; the error lists directories already prepared, whose metadata is preserved. After preparation, adoption pairs the chosen host once, creates the member in `provisioning`, provisions its project map, starts the process, records its endpoint, and enables it. A start failure keeps the slot in `provisioning` and reports `GOUZI_START_FAILED`; waking retries the start. Adoptions run one at a time. Retiring stops the member and its Resident process tree before archival; a working member cannot rest or retire. The [directory adoption decision](../../../.agents/notes/implemented/feature/2026-10-06-gouzi-directory-adoption.md) records execution and recovery semantics.

Adding a machine takes two requests so the user decides about trust before any login. `host-inspect` reads the key the machine presents without logging in and returns its fingerprint. `host-add` carries the fingerprint the user confirmed and the login password; the Provider refuses the machine if the key changed in between, logs in once, installs a dedicated key, and checks that DSH Desktop with the Gouzi agent is installed. The password travels only in that one same-origin request body, is not stored or logged, and is not part of any response. `host-remove` is refused while a live member lives on the host, and `browse` lists one folder level on a host. Every request that names a host needs the same manage permission as adoption.

`GouziHostService` is the Service Definition for hosts and for starting and stopping member processes on them. This package consumes it; the Desktop product provides it. A Server without the service lists members but reports `hostAvailable: false` and refuses adopt, wake, rest, and retire with `GOUZI_HOST_UNAVAILABLE`.

Config: Host `grantDeadlineMs` (default two hours, 60 seconds to 24 hours) is the lifetime of the execution grants issued to every member this panel creates. Host `roomPollIntervalMs` (default 2,000 ms, integer range 250 to 60,000 ms) is included in each successful `GouziRoomSnapshotV1` reply. While subscribed, the browser schedules its next read with that confirmed value; a later failed read retains the last successful interval and snapshot, marking the snapshot stale so it cannot authorize an addressed send. If the first read fails, no interval is known and no automatic timer is scheduled; the room offers “重新读取”. Unsubscribing aborts the read and fences late responses.

## Dispatch model configuration

`dispatcher` belongs to DSH plugin configuration, independently of the ordinary conversation model and Codex settings. Explicit `dispatcher.jev` supplies `provider` and `model` and takes precedence. Otherwise, a registered `dispatcher.jevProvider` (default `Jev`) uses its first configured model; registration without a model fails with `KENNEL_JEV_MODEL_MISSING`. The existing `llm-pi-ai` plugin can register this provider route and model. If that route is absent, `dispatcher.deepseek` selects the configured DeepSeek provider/model (defaults `deepseek-official` and `deepseek-flash`). Jev failures do not fall back. Only DeepSeek HTTP 402 or an explicit balance error normalized as `INSUFFICIENT_BALANCE` permits `dispatcher.codex` (default operator `codex`, optional model). Authentication, timeout, transport, and other failures remain failures. Codex makes only the scheduling judgment through the subscription Responses API with `toolChoice: none`; this creates no native Session. An omitted model is resolved from the actual registered model catalog. The direct path reads only existing authorized account authentication, loads no native configuration or MCP, and does not refresh an expired login. See the [direct Codex execution](../../physical-operator/resident-operator-local/README.md#direct-codex-model-execution) rules.

Limits belong to `dispatcher`; byte and reported token limits stop dispatch on observed overflow. The Codex SDK does not supply a backend hard output-token cap.

| Fields | Defaults | Scope |
|---|---|---|
| `maxTokens`, `maxOutputBytes`, `maxInputBytes`, `timeoutMs` | 512; 65,536 bytes; 65,536 bytes; 60,000 ms | Scheduling judgment. |
| `contextTokens`, `taskTimeoutMs`, `titleMaxChars`, `maxRunCandidates` | 8,192; 600,000 ms; 160; 20 | Task context, duration, title, and existing-run candidates. |
| `taskGenerationLimits.maxTokens`, `.maxOutputBytes`, `.maxToolCalls` | 4,096; 262,144 bytes; 40 | Aggregate task model generation. |
| `workspaceToolLimits.maxToolCalls`, `.maxFileBytes`, `.maxOutputBytes`, `.maxSearchFiles` | 40; 1,048,576 bytes; 262,144 bytes; 2,000 | Governed file operations. |
| `workspaceSnapshotLimits.maxFiles`, `.maxBytes`, `.maxBundleBytes`, `.timeoutMs` | 20,000; 268,435,456 bytes; 67,108,864 bytes; 120,000 ms | Directory checkpoint and bundle. |

## Model Experience

### Kennel scheduling judgment

#### What the model sees

The dispatcher issues an independent, tool-free model request containing the user objective, Host-qualified work/control candidates, and a fixed instruction to return only a candidate identity or clarification. Its configuration, prepared request, recorded output or failure, selection, submission, and admission receipt remain in session events. Task execution tools are absent from this scheduling request.

#### Token effect

For a qualified message, dispatch adds a bounded scheduling request before task start or control execution; explicit DeepSeek balance failure can add a Codex judgment request. `maxInputBytes`, `maxTokens`, and `maxOutputBytes` limit input bytes, reported output tokens, and observed output bytes. These limits do not measure token savings or provide a Codex backend hard output-token cap.

#### KV Cache effect

Room projections and display filters remain outside model context. Scheduling requests use their own fixed instruction and changing user/candidate input with independent model configuration; ordinary session model selection does not determine their route.

## Known Limitations and Deferred Work

- The room displays real user records, actual errors, and attributed task results. Each message selects one member; automatic decomposition across multiple dogs and long-term member chat memory are not provided. Members do not automatically chat with one another. Indeterminate execution requires reconciliation of the original run; the room does not redispatch unknown outcomes.
- A member on an SSH host reaches the main instance through a local SSH port forward and requires Gouzi agent protocol 2 and Remote Sync execution protocol 1.5. An older remote installation is explicitly refused; a version number alone does not prove protocol support. A per-host resource budget and re-pairing of a host belong to later phases.
- Task history is limited to this room’s source session. The room provides no cross-session member history or execution route outside standard TaskGraph nodes.
- The Settings roster is polled every three seconds while open and every twenty seconds otherwise. Room reads use `roomPollIntervalMs`; neither projection subscribes to scheduler events.

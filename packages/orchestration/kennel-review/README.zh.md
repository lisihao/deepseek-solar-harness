# `@deepseek-ai/dsh-kennel-review`

[English](README.md) | 中文

本包向[狗窝注册表](../ui-gouzi/README.md)（`ctx.kennelCollaborations`）注册 `review` 协作类型。评审是让其他成员阅读本会话中已完成的狗窝任务，并回复结论和意见。它是继 [`debate-orchestration`](../debate-orchestration/README.md) 中的 `debate` 之后的第二个类型，也说明了一个类型由什么组成：返回候选的 `offer` 和开始一个候选的 `start`。

## 提供什么

候选指向本会话中一个已完成的任务：已完成、有通过的 `work` 节点、并绑定到至少一个成员的 Run。只考虑最新的 `maxTargets` 个这样的任务，每个任务最多有 `maxReviewers` 个评审人。

- 评审人是已启用的成员，在支持文件工具和生成限制的入口上持有该任务的项目，并运行其固定的模型。做过这个任务的成员不会评审它。评审人按注册表顺序选取。
- 用户点名了某个成员时，只有该成员是评审人，且仅当该成员没有做过这个任务。
- 候选 id 写明 Run、它的 revision，以及每个评审人的 generation、入口和模型，所以任务变化或评审人变化都会让这次选择过期，调度器随后会拒绝它。

## 启动什么

该类型从任务的事件中读取 `work` 节点被接受的结果，然后编译并启动一个为每个评审人设一个节点的 TaskGraph。每个节点固定在其评审人的入口和模型上，可读取工作区，没有写入、执行、网络或费用预算。该图用 `gouziRecipient`（一个评审人）或 `gouziRecipients`（多个）准入，所以 daemon 会逐个检查可用性、工作区和授权。评审人并行运行，彼此看不到对方的意见。每条回复以 `结论：通过` 或 `结论：需要修改` 一行开头，其后每个问题一条意见；房间会把它显示并归属到评审人。评审不会修改被评审的任务。

Host 的资源限制（上下文 token、任务超时、生成和文件工具限制）随请求一起传入，所以本包没有自己的限制。`maxReviewers` 和 `maxTargets` 是仅有的配置。

## Model Experience

### 评审节点

#### 模型看到什么

评审人看到自己的成员名、做这个任务的成员名、任务标题、任务被接受结果的有界预览、用户的消息，以及一条指令：对照任务检查结果，必要时读取工作区文件，并以 `结论：通过` 或 `结论：需要修改` 开头。它有文件读取工具，没有写入、shell 或网络工具。

#### Token 影响

每个评审人增加一次有界提示：任务标题、结果预览和用户的消息，受 Host 的上下文和生成限制约束。评审人并行运行，各自承担自己提示的费用。

#### KV Cache 影响

不假定跨节点缓存；每个评审节点都是独立请求。

## 已知限制与延后工作

- 评审读取的是任务结果的预览，而不是完整的证据产物；已交付的文件只能通过评审人的文件工具读取。被 daemon 截断的结果按截断后的内容评审。
- 结论行是回复文本里的约定。房间把它显示为文本，没有代码把它当作裁决读取，评审也不会重新打开或阻塞被评审的任务。
- 只有由狗窝调度启动的任务（带 `work` 节点）可以被评审。辩论和其他评审不会被提供。
- 评审人按注册表顺序选取；除了点名某个成员，用户暂时不能指定评审人。

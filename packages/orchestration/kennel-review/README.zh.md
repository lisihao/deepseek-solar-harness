# `@deepseek-ai/dsh-kennel-review`

[English](README.md) | 中文

本包向[狗窝注册表](../ui-gouzi/README.md)（`ctx.kennelCollaborations`）注册 `review` 和 `rework` 两个协作类型。评审是让其他成员阅读本会话中已完成的狗窝任务，并回复结论和意见；返工是把任务连同要求修改的评审意见交还给原作者。它们继 [`debate-orchestration`](../debate-orchestration/README.md) 中的 `debate` 之后，也说明了一个类型由什么组成：返回候选的 `offer`、开始一个候选的 `start`，以及可选的、说明协作结果如何的 `outcome`。

## 提供什么

候选指向本会话中一个已完成的任务：已完成、有通过的 `work` 节点、并绑定到至少一个成员的 Run。只考虑最新的 `maxTargets` 个这样的任务，每个任务最多有 `maxReviewers` 个评审人。

- 评审人是已启用的成员，在支持文件工具和生成限制的入口上持有该任务的项目，并运行其固定的模型。做过这个任务的成员不会评审它。评审人按注册表顺序选取。
- 用户点名了某个成员时，只有该成员是评审人，且仅当该成员没有做过这个任务。
- 消息里提到成员时，就由这些成员按提到的顺序评审，不会换成别人：做这个任务的人会从名单中去掉，被提到的成员无法评审时不提供评审，而不是换成别的评审人，提到的人数超过 `maxReviewers` 也会被拒绝。只提到了作者（作为评审对象）的消息使用默认评审人。
- 候选 id 写明 Run、它的 revision，以及每个评审人的 generation、入口和模型，所以任务变化或评审人变化都会让这次选择过期，调度器随后会拒绝它。

## 启动什么

该类型从任务的事件中读取 `work` 节点被接受的结果，然后编译并启动一个为每个评审人设一个节点的 TaskGraph。每个节点固定在其评审人的入口和模型上，可读取工作区，没有写入、执行、网络或费用预算。该图用 `gouziRecipient`（一个评审人）或 `gouziRecipients`（多个）准入，所以 daemon 会逐个检查可用性、工作区和授权。评审人并行运行，彼此看不到对方的意见。每条回复以 `结论：通过` 或 `结论：需要修改` 一行开头，其后每个问题一条意见；房间会把它显示并归属到评审人。评审不会修改被评审的任务。

Host 的资源限制（上下文 token、任务超时、生成和文件工具限制）随请求一起传入，所以本包没有自己的限制。`maxReviewers` 和 `maxTargets` 是仅有的配置。

## 结论

回复的第一行就是结论：`结论：通过` 或 `结论：需要修改`（接受英文冒号和空格）。第一行是其他内容时，该评审人的结论为不明。评审的 `outcome` 把各评审人的结论汇总到被评审任务上：

- 任一评审人要求修改，任务为 `negative`，房间显示 `评审：待修改（名字）`。
- 所有评审人都通过，任务为 `positive`（`评审：已通过`）。
- 评审人失败、没给出结论或还没回复时，结果为 `unclear`；评审未结束时为 `pending`。

结论每次读取时由 Run 的结果计算，不单独存储，所以会随 Run 变化。它不会阻塞、重开或删除被评审的任务。

## 返工

评审要求修改后，`rework` 类型把任务交还给做这个任务的成员，每次评审只提供一次。该成员必须仍被调度器在同一项目、同一模式下提供（写入任务按写入任务返工），候选 id 写明这个提供项，所以成员变化会让选择过期。只有消息没有点名其他成员、且用户明确要求时才提供；不会自动返工。作者会收到任务标题、要求修改的评审人的意见（不含通过的评审人）和用户的消息；任务图由 Host 按成员自己的消息同样的方式构建，包括写入任务的文件范围、隔离和验证。返工后的任务就是普通的已完成任务，可以再次评审。原任务同时会显示 `已按评审意见返工`，它说明进度而不是通过。

## Model Experience

### 评审节点

#### 模型看到什么

评审人看到自己的成员名、做这个任务的成员名、任务标题、任务被接受结果的有界预览、用户的消息，以及一条指令：对照任务检查结果，必要时读取工作区文件，并以 `结论：通过` 或 `结论：需要修改` 开头。它有文件读取工具，没有写入、shell 或网络工具。

#### Token 影响

每个评审人增加一次有界提示：任务标题、结果预览和用户的消息，受 Host 的上下文和生成限制约束。评审人并行运行，各自承担自己提示的费用。

#### KV Cache 影响

不假定跨节点缓存；每个评审节点都是独立请求。

### 返工节点

#### 模型看到什么

作者看到自己的成员名、原任务标题、每个要求修改的评审人的意见（标明评审人）、一条要求修改并说明改了什么、没改什么以及原因的指令，以及用户的消息。它在该模式下使用与成员自己的任务相同的工具和限制。

#### Token 影响

作者一次有界提示，加上意见，意见长度受评审人输出限制约束。

#### KV Cache 影响

不假定跨节点缓存；返工是新任务。

## 已知限制与延后工作

- 评审读取的是任务结果的预览，而不是完整的证据产物；已交付的文件只能通过评审人的文件工具读取。被 daemon 截断的结果按截断后的内容评审。
- 结论从回复的第一行读取。措辞不同的评审人会被算作结论不明，而不是通过。
- 结论从存活会话的日志中读取，所以房间只在会话已加载时显示它。
- 返工适用于由一个成员完成、且该成员在同一模式下仍被提供的任务。由一组成员完成的任务可以评审，但不能返工。
- 只有由狗窝调度启动的任务（带 `work` 节点）可以被评审。辩论和其他评审不会被提供。
- 评审人按注册表顺序选取；除了点名某个成员，用户暂时不能指定评审人。
